- **ステータス**：応募用MVPの仕様整理（実装前・一部未確定）

## 1. 目的・コンセプト

**語学学校の運営業務を題材にした、日台バイリンガル対応のフルスタック業務管理システム**を制作する。

既存の語学学校向けシステムの業務知識・構想をベースに、Vueでのフロントエンド開発能力に加えて、API、PostgreSQLのDB設計、業務フローの設計・改善、技術文書化を示す。

### 応募において特に示したいこと

1. **Vue.jsを使った実務的なWebアプリ開発**
2. **PostgreSQLのデータ設計・管理**（外部キー・制約・Migrationなど）
3. **業務プロセスの理解とシステム化**（一覧・検索・登録・状態変更・集計）
4. **日本語・繁体字中国語での業務システム対応**
5. **コードの読みやすさ、変更しやすさ、基本的な品質管理**

### 想定する閲覧者

- 台湾側の採用担当者・現場エンジニア・管理職
- 日本人の管理職・関係者（閲覧する可能性はあるが、確定情報ではない）

公開デモ・README・ソースコードのそれぞれから、非技術者にもエンジニアにも価値が伝わる構成を目指す。

## 2. 題材と対象業務

### ベースにする既存の業務領域【方向性確定】

- レッスンスケジュール管理
- 生徒情報管理
- 講師・スタッフ情報管理
- 支払い記録管理

これらは既存システムの業務領域。**今回の応募用MVPにすべてを移植することは未決定**。

### 新たな中心機能【推奨案・最終範囲は未確定】

**講師の授業実績管理**を中心に、既存のレッスン予定データとつなぐ。

1. レッスンの予定を登録・確認する
2. 授業実施／欠席／キャンセルなどの実績を記録する
3. 講師別・月別に授業件数や実施時間を集計する
4. 必要に応じて管理用の一覧・レポートを表示する

**社員の出退勤打刻・休暇申請・承認**も話題に出たが、応募までの短期間では拡張候補とし、まずは授業予定と実績の連携を優先する案。

## 3. 応募用MVPの機能候補

以下は**実装優先度の提案**であり、現時点ですべての採用・完成を確約するものではない。

| 優先度 | 機能 | 仕様イメージ |
| --- | --- | --- |
| 最優先 | レッスン一覧 | 日付、講師、状態で検索・フィルタ |
| 最優先 | レッスン詳細・状態更新 | 予定／実施／欠席／キャンセル等を管理 |
| 最優先 | 授業実施記録 | 実施状況をAPI経由で保存 |
| 高 | 講師別の月間実績 | 月・講師別の授業数、時間、キャンセル件数の集計 |
| 高 | 日本語／繁体字中国語切替 | UIの主要文言と操作フローを両言語で提供 |
| 高 | 入力検証とエラー表示 | 必須項目・不正な状態遷移・APIエラー・空データ表示 |
| 高 | DB設計資料 | ER図、制約、Migration、Seedの説明 |
| 状況次第 | 生徒・スタッフ・支払い管理 | 既存内容を再利用しやすい場合のみ追加 |
| 応募後でも可 | 出退勤・休暇申請・承認 | 講師実績とは別の業務フロー |
| 応募後でも可 | 操作履歴・監査ログ・CSV | 運用面の品質向上 |

### 画面構成（推奨）

1. **レッスン管理**：一覧、検索、日付フィルタ、講師、状態
2. **授業実施・出欠記録**：実施、欠席、キャンセル等の登録・更新
3. **講師実績**：講師別・月別の集計結果

画面数を増やすより、**一つの業務フローが最後まで動くこと**を重視する。

## 4. 技術スタック

| 領域 | 技術 | 状態・補足 |
| --- | --- | --- |
| フロントエンド | **Vue 3 + TypeScript + Vite** | 採用方針 |
| UI | **Nuxt UI** | 採用方針。前職での使用経験を活用。Nuxt本体は必須にしない |
| 多言語化 | **vue-i18n（ja / zh-TW）** | 採用方針 |
| ルーティング | Vue Router | 推奨 |
| 共有状態 | Pinia | **検討中**。必要な共有UI状態に限定 |
| APIサーバー | **Hono** | 採用方針 |
| 入力検証 | Zod | 推奨 |
| DB | **PostgreSQL** | 求人に対応する主要技術 |
| DBアクセス・Migration | Drizzle ORM / drizzle-kit | 既存経験を生かす推奨構成 |
| DBホスティング | Neon | 採用。WorkersからNeon HTTP経由で接続 |
| APIクライアント | **OpenAPI + Kubb** | 採用。`/api/v1/doc` からFetchクライアントとVue Query Composableを生成 |
| サーバーデータ管理 | TanStack Vue Query | 任意。導入するならPiniaと役割を分ける |
| ユニットテスト | Vitest | 重要な業務ロジックに絞って推奨 |
| E2Eテスト | Playwright | 応募後でも可 |
| CI | GitHub Actions | 余裕があれば型チェック・テスト・ビルドを実行 |
| 公開先 | Cloudflare 等 | 候補。公開する場合は安全なデモ設定を優先 |

**設計上の注意**：API契約はOpenAPIを正とし、Kubbでクライアントを生成する。PiniaにAPI取得データを重複保持せず、サーバーデータはVue Queryへ寄せる。

## 5. PostgreSQLで見せたい設計

最低限の概念的なテーブル例：

- `teachers`：講師情報
- `students`：生徒情報
- `lessons`：講師・生徒・日時・状態
- （必要になれば）`lesson_records`：実施・出欠に関する詳細

以下のポイントを優先する。

- 主キー、外部キー、NOT NULLなどの基本制約
- 授業開始・終了時刻などの整合性
- 日付・講師別検索に適切なIndex
- Drizzle schemaとMigrationのGit管理
- 架空のSeedデータ
- 月間実績は、可能ならPostgreSQL側で集計する
- READMEに小さなER図を載せる

実装済みのテーブル・カラム・制約は `docs/db/database-design.md` と各テーブル仕様書を正とする。キャンセル時の集計ルールはAPI実装時に確定する。

## 6. ログイン・公開デモの方針

**応募用MVPではログイン・認証機能を原則省略**する方向。

理由：

- 採用担当者がすぐ画面を試せる
- Vue・DB・業務ロジックの実装に時間を集中できる

ただし、認証なしの書き込みAPIを無制限に公開しない。

**公開方法の候補**：

- **閲覧専用デモ**を公開し、更新操作はローカルで動作確認できるようにする
- または**デモ専用の架空データ**に限定し、操作制限・リセットを設ける

本番導入時には認証・認可・監査等が必要であることをREADMEに明記する。公開リポジトリやデモDBに実在する学校関係者の情報・決済記録を持ち込まない。

## 7. GitHub・開発の進め方

### リポジトリ構成【方向性】

1. **Privateの練習用リポ**：試行錯誤、Vue/Nuxt UI/Hono/DBの検証を自由に実施
2. **Publicの提出用リポ**：完成・検証済みの実装を整理して公開

練習用のGit履歴は公開用へ引き継がなくてもよい。実装の移行はコードのコピー・整理でよく、**公開用の履歴は実際に行った作業を意味のある単位で記録する**。行っていないレビューや作業の履歴を装わない。

### 公開用リポジトリ名【未決定】

- `language-school-ops` — 題材が伝わり、最もおすすめの候補
- `portfolio-business-system` — 業務システムのポートフォリオという意味
- `portfolio-system` — シンプル・汎用的

**`language-school-ops` は提案された候補であり、最終決定ではない。**

### Git運用

- 機能ごとのコミットを使う（例：`feat: add lesson status update`）
- ブランチは当面 `main` + 必要に応じて `feature/*` で十分
- Issue / Pull Request：余裕があれば実際のタスクや変更を記録
- Git Tag：応募時点の版を `v0.1.0` などで固定することを推奨
- GitHub Release / CI：追加できれば加点だが、MVPより優先しない
